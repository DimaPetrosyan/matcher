# Матчер — соглашения проекта

Короткий свод правил, которые легко нарушить по невнимательности.
Подробности решений — в `~/Desktop/matcher-step-1-plan.md`.

## Именование

**Только camelCase** для всего, что объявляем мы: переменные, функции,
свойства объектов, поля типов, значения внутренних строковых объединений.

Два исключения, и оба — не наш выбор:

1. **Поля Telegram Bot API** — `parse_mode`, `reply_markup`, `callback_data`,
   `language_code`, `first_name`, `is_member`, `allowed_updates`. Их диктует
   протокол, переименовать нельзя.
2. **Имена в SQL** — таблицы и колонки в миграциях остаются snake_case, как
   принято в Postgres. В `schema.ts` они отображаются в camelCase:
   `tgChatId: bigint('tg_chat_id')`. Это граница, а не непоследовательность.

**Строковые значения, которые лежат в базе, менять нельзя** без миграции.
`'start_command'`, `'consent_given'`, `'deeplink_unknown'`, `'onboarding'` —
это данные, а не идентификаторы: они попадают в `audit_log.type`,
`app_user.source`, `app_user.status` и связаны check-констрейнтами.

Внутренние значения, которые никуда не сохраняются, — camelCase:
`MembershipResult = 'member' | 'notMember' | 'unverifiable'`.

## Языки

| Что | Язык |
|---|---|
| Логи, сообщения бросаемых ошибок | **английский** — их читает разработчик |
| Тексты для пользователя | через словари `src/i18n/locales/` |
| Комментарии в коде, названия тестов | русский |

**Любая новая строка для пользователя добавляется сразу в оба словаря** —
`ru.ts` и `en.ts`. Не «потом переведём»: русский словарь задаёт тип
`Dictionary`, поэтому пропуск в `en.ts` уронит компиляцию, и правка всё
равно не пройдёт. Добавляйте перевод в том же коммите.

Русский — эталонный: правим форму сначала в нём, потом компилятор укажет,
что доперевести.

**В словаре только строки — никаких функций и условий.** Словарь это данные,
которые однажды можно вынести в JSON или отдать переводчику.

- Переменная внутри текста — `{плейсхолдер}`:
  `'Он работает только для участников «{community}».'`
- Два варианта текста — два ключа (`denied` и `deniedInCommunity`),
  а выбор между ними делает слой рендера. Это решение о показе, а не данные.
- Подстановку выполняет `format()`; неизвестный плейсхолдер остаётся в тексте
  как есть — видимое `{community}` лучше молча пропавшего названия.
- Плейсхолдеры обязаны совпадать во всех языках. Компилятор этого не ловит,
  ловит тест в `test/i18n.spec.ts`.

Новый язык: файл в `src/i18n/`, строка в `locales`, строка в `dictionaries`
внутри `i18n/index.mts`.

## Схема базы

**Источник истины — SQL в `src/database/migrations/`.** `src/database/schema.mts` производный:
генерируется через `bun run db:pull` из живой базы и руками не правится —
правки сотрёт следующий пулл.

**Раннера миграций пока нет.** На пустом томе схему накатывает сам Postgres:
`src/database/migrations` смонтирован в `/docker-entrypoint-initdb.d`.
Но это срабатывает **только при инициализации новой базы** — новые файлы
на существующем томе придётся применять руками.

Отсюда: файлы должны быть исполнимым SQL целиком, без разметок
`-- Up/Down Migration` — Postgres выполнит файл до конца.

Порядок: написать SQL → накатить (сам или руками) → `bun run db:pull`.

Всё DDL — с `if not exists`, вставки — с `on conflict do nothing`: повторный
прогон файла безопасен.

**Но это защита от «накатил дважды», а не от «поменял и накатил заново».**
Если дописать колонку в уже применённый файл, `create table if not exists`
молча ничего не сделает, и вы будете думать, что изменение прошло.
**Изменения схемы — всегда новым файлом**, старые не редактируем.

## Раскладка

Рантайм — Bun, фреймворка нет. Файлы `.mts`, импорты с явным расширением:
`from "./env.mts"`. Шага сборки для разработки нет, `.env` читает сам Bun,
тесты — встроенный `bun test` с импортами из `bun:test`.

```
src/
  index.mts     запуск и остановка
  env.mts       переменные окружения
  database/     всё, что трогает таблицы
  bot/          всё, что нужно для работы бота
  i18n/         словари и переводчик
```

**В каждой папке `index.mts` — барель**: перечисляет то, что папка отдаёт
наружу. Снаружи импортируют только через него.

Два правила вокруг барелей, оба проверяются `test/boundaries.spec.mts`:

- **Внутри папки файлы импортируют друг друга напрямую**, не через
  собственный барель. Иначе получаются круговые импорты.
- **Тесты берут конкретный модуль, а не барель.** Барель тянет за собой
  соседей, а те создают синглтоны (`bot`, `client`) и требуют `env` —
  импорт одного модуля инициализировал бы всё приложение.

Логи — `console.log` / `console.warn` / `console.error`, без библиотеки.

**Вся конфигурация — в `.env`, и он в `.gitignore`.** Шаблона в репозитории нет,
список переменных живёт в README. Настоящие переменные окружения перекрывают файл,
поэтому на сервере значения задаются ими.

`env` — модульная константа, а не результат функции: импортируется где нужно
и падает на старте, если переменных не хватает.

## Границы

`src/database/**` не импортирует `grammy` и ничего из `bot/` — слой данных
не должен уметь отправлять сообщения. `src/i18n/**` не зависит ни от чего,
кроме себя.

Стережёт это `test/boundaries.spec.mts` — единственный рубеж, его надо
чинить, а не отключать.

`screens.mts` — чистые функции: переводчик и данные приходят аргументами,
никаких обращений к базе.

## Неочевидные места

Комментариев в коде нет, поэтому то, что по нему не восстанавливается, — здесь.

**`void bot.start()`, не `await`.** Это сам цикл поллинга, он никогда
не завершится: с `await` запуск приложения повиснет навсегда.

**`onConflictDoNothing({ target })` — `target` обязателен.** Без него
`ON CONFLICT` проглотит конфликт по любому ограничению, а не только по `tgId`.

**После `do nothing` нужен второй запрос.** При конфликте `returning`
возвращает пусто, существующую строку Postgres не отдаёт. Её добирают
селектом — иначе неоткуда взять `userId` для членств и журнала.

**`consentAt: sql\`now()\`, не `new Date()`.** В той же строке `created`
заполняется дефолтом `now()` на стороне базы; две отметки времени в одной
записи должны быть от одних часов.

**Три исхода проверки членства, не два.** `unverifiable` — наш операционный
сбой (бот не админ, чат не найден, Telegram недоступен), а не отказ
пользователю. Пускать при нём нельзя: иначе недоступность Telegram
становится дырой в закрытом контуре.

**`checkAll` пускает при частичном сбое.** Член хотя бы одного сообщества —
пускаем, даже если другая проверка не выполнилась. Отказ только когда все
проверки прошли и ни одна не дала членства.

**Членство перепроверяется на «Поехали».** Между `/start` и нажатием человек
мог выйти из чата, а состояние между экранами не хранится принципиально.
Слаг в `callback_data` нужен только для атрибуции, доступ им не даётся.

**Первый middleware отсекает не-личные чаты.** Люди набирают `/start`
в общем чате; без проверки бот ответит приветствием в группу.

**`400 message is not modified` — успех, не ошибка.** Повторное нажатие
даёт тот же текст.

**`setupDb()` вызывается до `startBot()`.** Порядок важен: если база
недоступна или схема не накатана, процесс должен упасть **до** того, как
поллинг заберёт первые апдейты. Иначе Telegram отдаст их, а обработать
их будет нечем — и они пропадут вместо того, чтобы дождаться починки.

Туда же со временем попадёт всё, что нужно подготовить перед стартом:
раннер миграций, прогрев справочников.

**Доступ определяет членство, не ссылка.** `/start` проверяет человека
по всем активным сообществам. Payload диплинка (`c-<id чата>`) нужен только
для атрибуции — какой чат привёл человека. Проверять членство лишь
в сообществе из ссылки нельзя: пересланное приглашение отказало бы
законному участнику соседнего чата.

**Прокси нет.** Сервер за пределами РФ, Telegram доступен напрямую.
Если хостинг однажды переедет в РФ — вернуть агент в `telegram/client.ts`
через `client.baseFetchConfig.agent` (grammY на Node принимает именно
`agent`, а не undici-`dispatcher`).

**`allowed_updates` перечисляется явно.** Когда понадобится `chat_member`,
его придётся дописать руками, иначе выходы из сообщества не придут.

**Неизвестный `callback_data` — не ошибка.** Гасим часики и молчим:
это и есть версионирование кнопок, старая клавиатура ничего не ломает.

**Членства только добавляются.** Выход из сообщества — отдельный сценарий
через `chat_member`, а не молчаливое удаление строки при регистрации.

## Идемпотентность

Отдельной таблицы обработанных апдейтов нет. Long polling даёт at-least-once,
значит **каждая операция обязана быть идемпотентной по своему естественному
ключу**: `on conflict do nothing`, `update … where status = …` и подобное.

Осторожно со счётчиками: инкремент идемпотентным не бывает. Если понадобится
счётчик — считать значение запросом по `audit_log`, а не хранить колонкой.
